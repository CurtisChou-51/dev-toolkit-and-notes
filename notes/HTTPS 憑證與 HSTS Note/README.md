# HTTPS 憑證與 HSTS Note

- 背景：最近在處理網站弱點掃描，報告裡有一條是 `Strict-Transport-Security` 標頭沒設，設定上加一行就結束。就「少一行回應標頭為什麼會被算成一條弱點」這個問題往下追，順便把 HTTPS 憑證與 HSTS 之間的關係一起釐清補齊

## 憑證是什麼

> [!NOTE] 
> 一句話：憑證就是網站的身分證，上面寫著「我是 `example.com`，我的公鑰是這一把」，再由一個瀏覽器事先就信任的機構（CA）蓋章背書

- 憑證本身不加密任何東西，它是一份**被 CA 簽過章的聲明**，內容是「這個網域的公鑰是這一把」。HTTPS 的安全，建立在「信任哪些簽發者」之上

### 憑證做的兩件事

1. 身分驗證：CA 的簽章 + 網域名稱 + 有效期，解決的是「使用者沒連到假網站」
2. 交付公鑰：伺服器的公鑰，讓後續能安全地建立加密通道

- 缺了身分驗證，加密就沒意義，使用者可能正在跟冒充者安全地通訊

### 瀏覽器收到憑證時檢查什麼?

1. **簽發者**在我的信任清單裡嗎?（根憑證／CA）
2. **網域名稱**跟我要去的一致嗎?（`google.com` 的憑證不能用在 `g00gle.com`）
3. **有效期**還沒過嗎?
4. 有沒有被**撤銷**?

- 任一項不過就是紅色警告頁
- 「信任清單」是作業系統或瀏覽器內建的根憑證庫，這是整個體系的信任起點，也是它的弱點所在

### 公鑰與私鑰，以及它們在 HTTPS 握手裡的位置

| 目的    | 誰動手  | 用哪把                            | 方向   |
| ------ | ------ | -------------------------------- | ----- |
| 保密    | 寄件人  | 收件人的**公鑰**加密 → 私鑰解密      | 多對一 |
| 證明身分 | 本人   | 自己的**私鑰**簽章 → 公鑰驗章        | 一對多 |
| 協商金鑰 | 雙方   | 各自私鑰 + 對方公鑰（ECDH）          | 對等   |

把上面那張表對到一次實際的 TLS 握手：

1. CA 簽發憑證、瀏覽器驗章 → 表格的「證明身分」
2. 伺服器用私鑰簽 CertificateVerify，證明自己真的持有憑證上那把公鑰 → 還是「證明身分」，不是解密
3. 雙方用 ECDHE 算出這次連線的對話金鑰 → 表格的「協商金鑰」
4. 之後的資料傳輸交給 AES 這類對稱加密，公私鑰到這裡就退場了

- 表格第一列的「保密」，也就是最經典的「公鑰加密、私鑰解密」，在整個握手裡完全沒出現。TLS 1.2 時代還留著的 RSA 金鑰交換，已經被 TLS 1.3 移除
- 移除的原因是它沒有前向保密，私鑰一洩漏，過去錄下的流量全部可解
- 前向保密（Forward Secrecy）：ECDHE 每次連線現場算出臨時金鑰，用完就丟，從未在網路上傳輸。即使日後拿到伺服器私鑰，也解不開當時的錄影

### 保證與不保證

- 保證：
  - 傳輸內容沒人看得懂
  - 對方是憑證上寫的那個網域
  - 資料沒被中途竄改
- 不保證：
  - 這個網站是好人
  - 這間公司誠實
  - 伺服器端安全、不會外洩
- 詐騙網站也申請得到憑證，憑證驗證的是「身分」，不是「品行」

### 中間人攻擊與 Fiddler：靠的是信任

```text
瀏覽器 ──TLS①──> Fiddler ──TLS②──> 真伺服器
```

- 兩段都是真加密，Fiddler 看得到明文，純粹因為它同時是兩段連線的端點
- 它唯一需要跨過的門檻，就是讓使用者信任它偽造的憑證，而作法就是安裝 Fiddler 的根憑證到信任清單

同樣的原理往外推：

- 公司的 SSL 檢查（Zscaler、Palo Alto、防毒軟體）**原理完全相同**，公司筆電預裝了公司根憑證，所以 IT 看得到所有 HTTPS 內容
- 安裝來源不明的根憑證，是把**「冒充任何網站」的權力**交給對方，不只是多信一個站
- **CA 被入侵是災難級事件**。2011 年 DigiNotar 被攻破後簽出假的 Google 憑證用於監聽，結果整間 CA 被所有瀏覽器除名、公司倒閉
- 加密強度再高，都擋不住「信錯了人」

### Fiddler vs Wireshark

| 特性   | Fiddler 類（代理）   | Wireshark（側錄）     |
| ----- | ------------------- | ------------------- |
| 角色   | **主動**插入當端點    | **被動**旁聽封包      |
| 明文   | 看得到，天生就是明文   | 看不到，只有亂碼      |
| 前提   | 使用者信任它的根憑證   | 無                  |

## HSTS 是什麼

> [!NOTE] 
> 一句話：HSTS 就是網站交給瀏覽器的一張便條，上面寫「以後找我一律直接走 HTTPS，不要再用 HTTP 問一次」，而這張便條是記在使用者自己的電腦裡

- HSTS（HTTP Strict Transport Security，RFC 6797）是伺服器回傳的一個 HTTP 回應標頭，用來告訴瀏覽器：「接下來這段時間內，連我這個網域一律只准用 HTTPS」

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains
```

- 瀏覽器收到後會把這條規則記在**本機**，後續所有對該網域的連線都在本機先強制改成 https

### HSTS 解決的兩個問題

#### 問題一：SSL Stripping（降級攻擊）

- 沒有 HSTS 時，使用者在網址列打 `example.com`，瀏覽器會先送一個**明文 HTTP** 請求出去，再由伺服器 301 轉址到 HTTPS
- 整場攻擊的命脈就在這個明文封包：
  - 同網段的攻擊者攔下它，自己跟真實伺服器建 HTTPS
  - 對使用者這端維持 HTTP，並把回傳內容裡的 `https://` 全部改寫成 `http://`
- 使用者看到的網頁一模一樣，只是網址列沒有鎖頭，而多數人不會看

攻擊流程：

```text
① 使用者打 example.com
② 瀏覽器 → 送出 http://example.com        ← 明文，攻擊者看得到也改得到
③ 攻擊者攔下，自己去跟真的伺服器建 HTTPS
④ 攻擊者把伺服器回來的 https:// 連結全部改寫成 http://
⑤ 使用者繼續在 http 上操作，密碼直接進攻擊者口袋
```

HSTS 讓那個可被攔截的封包從一開始就不存在：

```text
① 使用者打 example.com
② 瀏覽器查自己本機的 HSTS 清單 → 找到 example.com
③ 內部直接改成 https://example.com（Chrome 記為 307 Internal Redirect）
④ 送出的第一個封包就是 TLS Client Hello
```

- 第 ② 步整個被跳過，網路上沒有任何明文 HTTP 請求可以攔，攻擊者沒有東西可以剝

#### 問題二：使用者點掉憑證警告

明文那條路被堵死後，攻擊者的下一招是硬做假憑證。平常瀏覽器跳紅色警告頁，但下面有「進階 → 繼續前往（不安全）」，使用者多半會直接按下去

- HSTS 生效的網域這顆按鈕會消失。規範要求把 TLS 錯誤視為致命錯誤，不給使用者繞過

### HSTS 的三條關鍵規則

1. 標頭只在 HTTPS 回應中有效，純 HTTP 回應送來的一律忽略 → 中間人無法偽造或塞入 HSTS
2. 這條 TLS 連線若有任何憑證錯誤，標頭也必須被忽略 → 純自簽憑證的站台永遠註冊不了 HSTS
3. 規則存在使用者的瀏覽器裡，記滿 `max-age` 秒 → 送出去就收不回來，這是最大的部署風險

- 第二條是最容易被忽略、卻最常用來解釋怪現象的一條，也剛好接回前半篇：HSTS 沒有自己的信任來源，它整個站在憑證鏈驗證通過這個前提上

### HSTS 參數

| 參數                   | 說明                                                    |
| --------------------- | ------------------------------------------------------- |
| `max-age=31536000`    | 必填。有效秒數，一般設一年。弱掃常把低於半年或一年算一條          |
| `includeSubDomains`   | 選填。部署前最大的地雷，所有子網域都會被一起鎖住                |
| `preload`             | 選填。配合送審 hstspreload.org，補上「第一次造訪」的缺口         |

### HSTS 擋不住什麼

- 第一次造訪：HSTS 是 Trust On First Use，瀏覽器得先成功連過一次 HTTPS 才知道規則。全新使用者、剛清過瀏覽資料的電腦、無痕模式，第一次都還是裸的，Preload List 就是為了補這個洞
- 相似網域：攻擊者導去 `examp1e.com`，那是別的網域，管不到
- 非瀏覽器用戶端：手機 App、curl、後端對後端 API 多數不實作 HSTS，那邊得靠憑證綁定或程式裡指定 https

### HSTS 排錯

已經被鎖住要臨時解開：

- **Chrome / Edge**：開 `chrome://net-internals/#hsts`，最下方 **Delete domain security policies** 填主機名稱送出
- **Firefox**：歷史紀錄找到該站台 → 右鍵「忘記此網站」

兩者都對 Preload List 裡的項目無效。
